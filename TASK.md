## Контекст

В экосистеме сервисы общаются через брокер сообщений (Kafka/AMQP/MQTT/WebSocket), и каждый
сервис-потребитель и сервис-поставщик описан спецификацией **AsyncAPI 3.0**. Нужен способ в CI,
**до мержа PR потребителя**, детерминированно ответить: совместим ли потребитель с текущей спекой
поставщика по тем каналам, которые он использует — без поднятия брокера и без запуска сервисов.

Несущий инвариант тот же, что у sync-валидатора: каждый сервис конформен своей спеке (доказано его
компонентными тестами) ⇒ структурная совместимость спек-пары = реальная совместимость сервисов.
Проверка статическая, детерминированная, запускается в CI и гейтит мерж машиночитаемым exit-кодом.

Отличие async от sync (задаёт уникальность, а не копию openapi): единица проверки — не HTTP-операция,
а **канал** (topic/queue) и **операция с действием send/receive**; транспорт задаётся **протоколом**
из серверов спеки (kafka/amqp/mqtt/ws); поддерживаются **три паттерна коммуникации** — request-reply,
fire-and-forget, publish-subscribe; в игре async-специфика — correlationId, reply, contentType,
headers сообщения. У потребителя есть **полная AsyncAPI-спека** (а не реконструированный контракт).

## Что нужно

CLI-инструмент, который принимает путь к конфигу и проверяет совместимость пары consumer↔provider:

1. **Читать конфиг** contract-tests.yaml: спека потребителя (локальный файл), список используемых
   потребителем каналов, спека поставщика (URL или файл), настройки (таймаут, сохранять ли JSON-отчёт,
   имя файла отчёта, уровень логирования).
2. **Парсить обе AsyncAPI 3.0 спеки** (потребителя и поставщика), включая резолвинг $ref.
3. **По каждому каналу потребителя** из конфига: определить его протокол (через серверы), извлечь
   исходящие/входящие сообщения из операций (учитывая send/receive и reply), найти у поставщика
   соответствующий канал и определить паттерн коммуникации.
4. **Сверить сообщения** по паттерну: для request-reply — и запрос, и ответ; для fire-and-forget —
   только запрос; для pub-sub — только сообщение подписки. Сверка учитывает contentType,
   correlationId, множество обязательных полей и типы полей (рекурсивно: вложенные объекты, массивы, $ref).
5. **Вынести вердикт** compatible/incompatible с указанием, какой канал/операция/поле не сошлись, и
   отдать структурированный отчёт (stdout + опционально JSON-файл) в каноне экосистемы
   (симметричном pinout-openapi: тот же schema_version, errors[]; subject = имя канала).
6. **Вернуть машиночитаемый exit-код**, по которому CI гейтит мерж.

Инструмент НЕ поднимает брокер и не гоняет тесты; НЕ детектит breaking-change во времени
(provider v1→v2 — отдельный инструмент); НЕ проверяет конформность сервиса своей спеке
(это компонентные тесты самого сервиса).

## Definition of Done

- `go build ./...` и `go vet ./...` зелёные; команда `validate <config.yaml>` запускает реальный
  пайп (парсинг обеих спек → сверка каналов → вердикт), а не заглушку.
- Совместимая пара → вердикт compatible, exit 0; несовместимая → вердикт incompatible с указанием
  канала/поля, отдельный exit-код.
- Ошибки входа различимы по exit-кодам и error.code (конфиг невалиден; файл спеки не найден;
  спека непарсится; URL поставщика недоступен/не-2xx; таймаут загрузки) — таксономия согласована
  и симметрична pinout-openapi (напр. 0 compatible · 1 incompatible · 2 config · 3 io/parse).
- Покрыты компонентными сценариями happy-path + все ветки отказа адаптера; юнит-тестами — ядро
  сверки сообщений (протокол, паттерны, required-поля, типы, correlationId).
- JSON-отчёт валиден против замороженной схемы отчёта; конфиг — против замороженной схемы конфига;
  формат отчёта совпадает с pinout-openapi (различается только interaction: "async" и subject).
- README описывает назначение, CLI-форму, конфиг, формат отчёта и карту отказов.

## Ограничения

- Стек: Go + cobra (CLI). Парсинг AsyncAPI 3.0 — честной библиотекой/парсером с поддержкой $ref
  (выбор носителя — на этапе проектирования).
- Один внешний вход — вызов CLI `validate <config.yaml>` (одноразовый, детерминированный).
- Симметрия с sibling-проектом pinout-openapi по конфигу, формату отчёта и exit-кодам обязательна.
- Без тестовых сред: инструмент — статическая функция в CI.

## Открытые вопросы (НЕ решать здесь — их задаёт оператору @gilb на фронт-доре)

Реальные неоднозначности исходного репозитория; оставлены фронт-дору `@gilb`
(`skills/roles/gilb/gilb.md`) для элицитации у оператора, не зашиты в требование:

1. Один канал или все перечисленные в `consumer.channels` (исходник брал только первый «для простоты»).
2. Матч канала поставщика — по протоколу (как в исходнике, имя игнорируется) или по имени/адресу.
3. Семантика required-полей — идентичность множеств (исходник) или вложение/variance по паттерну
   (как в pinout-openapi).
4. Таксономия и мап на exit-коды (сейчас в исходнике только 0/1) — зафиксировать симметрично openapi.
5. Источник спеки поставщика (url XOR path или оба) и авторизация (Bearer/token для приватного git).
6. Что именно сверять в сообщении: payload + headers + correlationId + contentType; глубина субтайпинга.
7. Роль `settings.ignore_warnings` / `log_level` — диапазон, дефолт, error.code на невалид.
8. Границы MVP: все три паттерна коммуникации в v1 или начать с request-reply; inline-сообщения vs
   только `#/components/messages`.
